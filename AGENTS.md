# AGENTS.md

Rules for agents working in this repo. Read them before changing `plugins/alf/`.

## Layout

- `plugins/alf/upstream/<upstream>/<skill>/`: a byte-for-byte copy of one upstream skill folder.
- `plugins/alf/upstream/<upstream>/LICENSE` and `PIN.md`: the upstream's license, and one row per upstream skill with its commit and whether it is pinned.
- `plugins/alf/skills/<skill>/SKILL.md`: either a wrapper that points at an upstream skill, or an in-house skill. A wrapper's frontmatter is copied from the upstream skill, and its body points at the upstream skill. A wrapper can have a different name from its upstream skill folder; the `Wrapper` column in `PIN.md` gives that name.
- `scripts/update-upstream.sh`: changes upstream skills. `task update-upstream` and the weekly workflow both run it. It rebuilds `dist/` before it commits.
- `plugins/alf/skill-dependencies.txt`: the skills each skill calls by name (`<skill>: <dependency> ...`), and the names it only mentions (`<skill> mentions: <name> ...`).
- `dist/skills/<skill>/`: one self-contained APM bundle per skill. Generated by `scripts/build-apm.sh`.
- `dist/user-apm.yml`: generated. Lists every skill, for a single user.

## Editing rules

- Change files under `plugins/alf/upstream/` through `scripts/update-upstream.sh`.
- Add local instructions to a wrapper between its `<!-- overlay:start -->` and `<!-- overlay:end -->` markers. The script regenerates the frontmatter and the pointer line.
- Never edit `dist/` by hand. Run `task build-apm` after a change under `plugins/alf/`, and commit `dist/` with it.
- When a skill names another skill, list that name in `plugins/alf/skill-dependencies.txt`: under the skill as a dependency if it calls the skill, or under `mentions` if it does not. The build fails on any unlisted name.

## Writing style

Write like a technical writer. State facts, steps and decisions. Cut anything else.

- Lead with the point. Keep sentences short.
- Name the exact file, command or field. Use specific verbs: "writes", not "handles".
- Use active voice. Write steps in the imperative: "Run the setup."

## Adding or updating upstream skills, or checking a PR that touches them

1. **License.** Read the upstream `LICENSE`. Tell the user its name and copyright line. If it is new, or changed since the last pin, say so. If it is missing, or not permissive (MIT, Apache-2.0, BSD-2/3-Clause, ISC, Unlicense, CC0), warn the user and suggest aborting that change.
2. **Dependencies.** For every changed upstream skill, list the other skills its files call or link to: any phrase that asks for another skill to be called or used by name (for example `call ... with "name"` or `the name skill`), `/name` references to skills, and relative links that leave the upstream skill folder. Each one must be an upstream skill with a wrapper in `plugins/alf/skills/`. Only names of skills count.
3. **Missing dependencies.** Report each missing one, and offer to add it as an upstream skill.
4. **Report, then ask.** Summarise what you found, and ask before committing or pushing.

## Commands

- `task update-upstream` moves unpinned upstream skills to latest.
- `task update-upstream SKILL=<name>` moves one upstream skill to latest.
- `task update-upstream SKILL=<name> REF=<sha or tag>` pins one upstream skill.
- Add `DRY_RUN=1` to any of these to print the plan.
- `scripts/update-upstream.sh add <upstream> <url> <path>...` copies new upstream skills in and writes the files.
- `task build-apm` rebuilds `dist/`.
- `task ci` checks `dist/` matches a fresh build, then scans the skills and upstream skills with SkillSpector (static, no LLM). CI runs the same task. `dist/` is not scanned separately: it is a build of the scanned sources.
- `task hooks:install` points this clone's git hooks at `.githooks`. Run it once per clone.

Each update opens a PR. Its description tells the reviewer to check LICENSE changes and missing linked upstream skills.

## Agent skills

### Issue tracker

Issues live in GitHub Issues for `olillevik/alf`, managed with the `gh` CLI. See `docs/agents/issue-tracker.md`.

<!-- alf:issue-workflow start -->
- **Spec from an existing ticket**: add the spec to that ticket's body under a `## Spec` heading, replacing any existing `## Spec` section. Apply the label for the `ready-for-agent` role (see `docs/agents/triage-labels.md`).
- **Spec with no existing ticket**: create a new ticket for the spec.
- **Implementation tickets** (for example from `to-tickets`): create each one as a sub-issue of the ticket it was based on, the existing ticket or the spec ticket. With no such ticket, create standalone tickets.
- **Sub-issue operation**: if `docs/agents/issue-tracker.md` describes a sub-issue feature, use it. If the tracker has no sub-issue feature, or it is switched off (for example raw markdown files), link both ways by hand: the child's body starts with `Part of <parent>`, and the parent's body gets a `## Child tickets` checklist with one `- [ ] <child>` line per child. This overrides to-tickets' rule against modifying the parent, for these links only. Do not change the parent's open or closed state.
<!-- alf:issue-workflow end -->

### Triage labels

Default labels: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. See `docs/agents/triage-labels.md`.

Single-context: one `GLOSSARY.md` and `docs/adr/` at the repo root. See `docs/agents/domain.md`.
